# sync-gitlab-discord

FastAPI-сервис принимает GitLab webhooks и отправляет карточки в Discord.

## Уведомления

- **Merge Request:** одна карточка на MR. Первое событие создаёт сообщение, следующие редактируют его. Карточка показывает статус, Draft, ветки, ревьюеров, ответственных и последнее изменение. Из `changes` выводятся изменения заголовка, описания, назначений, меток, веток и готовности к ревью. Индивидуальное одобрение отличается от полного одобрения MR. Добавление коммита отражается отдельно.
- **Push:** фильтр веток, первые пять коммитов и общее количество из `total_commits_count`.
- **Комментарии:** отдельные сообщения со ссылкой непосредственно на комментарий. По умолчанию только MR и без системных комментариев.
- **Wiki:** создание, изменение и удаление страниц.

Все текстовые поля ограничиваются по индивидуальным лимитам Discord и общему бюджету embed. Упоминания пользователей и ролей отключены.

## Docker Compose

1. Скопировать `.env.example` в `.env` и заполнить `DISCORD_WEBHOOK_URL`.
2. Запустить из этой папки:

```bash
docker compose up -d --build
docker compose ps
docker compose logs --tail=100
curl --fail http://127.0.0.1:8081/health
```

GitLab webhook направить на `POST /gitlab` через существующий HTTPS reverse proxy. Контейнер слушает порт 8080, публикация на хосте — `127.0.0.1:8081`. Проверять доставку следует с самого GitLab; локальный `/health` проверяет процесс и SQLite.

Включить события Merge request, Push, Comments и Wiki page в настройках GitLab Webhooks. Сервис не опрашивает GitLab API и не требует GitLab API token.

## Настройки

| Переменная | Значение |
| --- | --- |
| `DISCORD_WEBHOOK_URL` | Обязательный HTTPS URL вебхука Discord. Поддерживается `?thread_id=...`. |
| `ALLOWED_PUSH_REFS` | Полные refs через запятую. В Compose по умолчанию `refs/heads/develop,refs/heads/main`; пустое значение разрешает все ветки. |
| `ONLY_MR_NOTES` | По умолчанию `1`: только комментарии к MR. |
| `IGNORE_SYSTEM_NOTES` | По умолчанию `1`: пропускать системные комментарии. |
| `STATE_DB_PATH` | Путь SQLite при локальном запуске, по умолчанию `data/relay-state.sqlite3`. Compose использует `/app/data/relay-state.sqlite3`. |
| `LOG_LEVEL` | `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL`; по умолчанию `INFO`. |
| `GITLAB_SECRET` | Сохранена для совместимости. Проверка входящего токена в текущую реализацию не входит. |

Булевы настройки принимают `1/0`, `true/false`, `yes/no`, `on/off`. Некорректная конфигурация останавливает запуск с указанием имени параметра.

`.env`, SQLite и локальные Python-окружения исключены из Git. В Docker build context входят только исходники, Dockerfile и зависимости. Не публикуйте вывод `docker compose config`: он содержит подставленные значения окружения.

## Хранение карточек MR

SQLite хранит соответствие «Discord webhook/thread + GitLab project + MR iid → Discord message ID» в именованном volume `relay-data`. Обычный перезапуск и пересборка контейнера сохраняют карточки. `docker compose down -v` удаляет volume и соответствия.

При удалении карточки из Discord следующее событие MR создаёт её заново. Смена токена того же вебхука сохраняет соответствие; другой webhook или thread получает отдельные карточки. Старые события с датой раньше последнего обработанного события пропускаются. Поддерживаются даты ISO 8601 и старый формат GitLab с `UTC`.

Запускайте **один worker и один экземпляр** сервиса: блокировки одновременного создания карточки действуют внутри процесса. Уведомления об изменениях редактируют существующую карточку и не поднимают её в конец канала. Комментарии приходят новыми сообщениями.

Карточки, отправленные старой версией сервиса, автоматически не подхватываются: для них нет сохранённых ID. При первом событии новая версия создаст новую карточку MR. Также возможен дубль при аварии между созданием сообщения в Discord и сохранением его ID в SQLite.

Очередь и автоматические повторы доставки не реализованы. При ошибке Discord сервис возвращает `502`, при недоступной SQLite — `503`; успешный ответ означает подтверждённую отправку или редактирование. Причину можно найти в логах по ID события.

## Диагностика

- `GET /health`: `200`, если доступна SQLite; `503`, если хранилище недоступно. В ответе — счётчики обработанных событий с момента запуска. Внешнее соединение с Discord здесь не проверяется.
- Docker healthcheck выполняет `/health` каждые 30 секунд.
- JSON-логи содержат `event_id`, `event_type`, `project_id`, `result`, `elapsed_ms`. Ошибки Discord дополнительно содержат `error_kind` и HTTP-код, без webhook URL и тела ответа Discord.
- Некорректный JSON возвращает `400`, некорректная структура известного события — `422`, неподдерживаемые события игнорируются с `200`.

## Локальный запуск и тесты

Python 3.11+; Docker использует Python 3.12. Зависимости и их транзитивные зависимости зафиксированы в `requirements.txt`.

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
Copy-Item .env.example .env
# Заполнить .env перед запуском.
.venv\Scripts\python -m uvicorn app:app --env-file .env --host 127.0.0.1 --port 8080 --workers 1
```

```powershell
.venv\Scripts\python -m unittest discover -s tests -v
```

Тесты запускают FastAPI с `httpx.MockTransport` и временной SQLite, без обращений к Discord/GitLab. Проверяются перезапуск, одновременные события, удалённые карточки, порядок событий, изменения MR, фильтры, ссылки, лимиты, валидация и ошибки доставки.
